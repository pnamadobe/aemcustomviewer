# AEM Assets View – Custom Main Preview Viewer (Browser Extension)

## Goal
Show proprietary file types that AEM Assets will never support in a custom, interactive viewer. The viewer is injected into the **main preview area** of the Assets View asset details page. The supported side-panel and header-menu extension points can't do this.

## Status
Project start. Unsupported approach (DOM injection into an Adobe-hosted SPA).

## Background
- Assets View is a hosted React micro-frontend that runs in an iframe inside Unified Shell (`experience.adobe.com`).
- UI Extensibility (App Builder) offers:
  - the details side panel (`aem/assets/details/1`)
  - the details header menu
  - browse action bar and quick actions
- None of these can replace or add to the main preview area.
- Asset Compute custom workers can produce static renditions, but not interactive viewers.

## Approach
A Chrome Manifest V3 extension (Tampermonkey for early prototyping) that:

1. **Targets the Assets View iframe**
   - The content script uses `all_frames: true`.
   - `matches` must cover the Assets View iframe origin, not only `experience.adobe.com`.
2. **Detects the asset details page**
   - Listens for SPA route changes (`popstate`, `hashchange`, `history.pushState` patch).
   - Uses a `MutationObserver` to know when the preview container is rendered.
3. **Identifies the asset**
   - Reads the asset ID or path from the URL or DOM.
   - Checks the MIME type or extension against an allowlist of proprietary types. Anything else is left alone.
4. **Gets auth**
   - Injects a page-context script (`chrome.scripting.executeScript` with `world: "MAIN"`).
   - The script wraps `fetch`/`XMLHttpRequest` to capture the IMS `Authorization` header from Assets View's own API calls.
   - It passes the token to the content script with `window.postMessage` (origin-checked).
5. **Fetches the binary**
   - Uses the same Assets API endpoints the app already calls (to be found with DevTools).
   - Streams or ranges large files where possible.
6. **Mounts the viewer**
   - Places an absolutely positioned overlay on the preview container. This is preferred over replacing nodes, because React re-renders would undo the replacement.
   - Re-checks position on resize and route change, and tears down on navigation away.
   - Includes a toggle to show the default Adobe preview.
7. **Fails safely**
   - If selectors or endpoints don't resolve, it does nothing, so the default UI stays intact.

## Proposed structure
```
extension/
  manifest.json          # MV3, host_permissions, all_frames content script
  src/
    content.ts           # route detection, DOM observation, overlay mounting
    page-hook.ts         # MAIN-world fetch/XHR interception for token capture
    assets-api.ts        # asset metadata + binary fetch
    selectors.ts         # ALL DOM selectors in one place (expect churn)
    viewers/
      index.ts           # mime/extension -> viewer registry
      <format>.ts        # per-format renderer (canvas/WebGL/WASM)
  ui/overlay.css
docs/
  discovery.md           # iframe origin, routes, API endpoints, DOM notes
```

## Risks
- **Unsupported:** Adobe Support won't help, and any release can break it.
- **Fragile DOM:** class names are generated by the build. Keep every selector in `selectors.ts` and prefer semantic anchors.
- **Security review:** capturing tokens needs sign-off from the security team. The token never leaves the user's browser, and it must not be logged or stored.
- **Distribution:** every user needs the extension. For managed teams, deploy through Chrome enterprise policy.
- **Platform hardening:** stricter CSP or iframe changes could block the approach.

## Complementary / fallback options
- **Asset Compute custom worker:** static thumbnails and renditions, so the native preview and grid views look right.
- **Header-menu extension:** a supported full-screen modal viewer, one click away.
- **Feature request to Adobe:** an extension point for the main preview area.
